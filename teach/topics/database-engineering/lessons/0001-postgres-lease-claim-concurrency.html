为什么两个 Worker 不会领取同一个 Job？

Why don't two workers claim the same job?

本节目标 / Goal

结合现有 PostgreSQL Job Lease，区分 MVCC 快照、行锁、SKIP LOCKED 和 Lease 所有权检查分别解决什么问题。我们不从基础 SQL 讲起；重点是解释并发保证及其边界。

Using the existing PostgreSQL Job Lease, distinguish the roles of an MVCC snapshot, a row lock, SKIP LOCKED, and the Lease ownership check. We will not start with basic SQL; the focus is on explaining the concurrency guarantees and their limits.

先看真实查询 / Start with the project query

WITH candidate AS (
  SELECT id
  FROM jobs
  WHERE status = 'pending'
     OR (status = 'running' AND lease_expires_at <= NOW())
  ORDER BY id
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE jobs AS j
SET status = 'running',
    lease_token = $1,
    lease_expires_at = NOW() + ($2 * INTERVAL '1 second')
FROM candidate
WHERE j.id = candidate.id
RETURNING ...

候选行的选择与更新在一条 SQL 语句里完成。这里没有显式的 Begin/Commit；在当前调用方式下，PostgreSQL 会在该语句的隐式事务中执行它。选中并锁定候选行、写入新状态和 token，要么一起提交，要么一起回滚。

Candidate selection and the update happen in one SQL statement. There is no explicit Begin/Commit here; with this call pattern, PostgreSQL executes the statement in an implicit transaction. Selecting and locking the candidate, then writing the new status and token, commit or roll back together.

四个机制，各司其职 / Four mechanisms, four responsibilities

  1. MVCC snapshot / MVCC 快照

    MVCC 决定一条语句能看到哪些已提交的数据版本。PostgreSQL 默认的 Read Committed 隔离级别通常为每条语句建立快照；它不代表“完全没有锁”。

    MVCC determines which committed row versions a statement can see. PostgreSQL's default Read Committed isolation generally takes a snapshot per statement; it does not mean that the database uses no locks.

  2. FOR UPDATE row lock / FOR UPDATE 行锁

    它锁住被选中的 Job 行，使冲突的领取或更新不能同时修改该行。锁在当前语句的事务结束时释放；本项目的 Worker 处理发生在领取语句之后，不持有这把行锁。普通 SELECT 不拿这种行锁，但会拿表级 ACCESS SHARE 锁；它通常不会阻塞行更新。

    It locks the selected job row so a conflicting claim or update cannot modify that row at the same time. The lock is released when the statement's transaction ends; this project's worker processes the job after the claim statement and does not hold this row lock while doing so. A plain SELECT does not take this row lock, but it does take a table-level ACCESS SHARE lock, which normally does not block row updates.

  3. SKIP LOCKED / 跳过已锁行

    另一个领取者遇到已锁候选行时跳过它，而不是等待。队列消费者因此可以继续找其他任务；如果没有其他可领取行，本次可能返回无行。代价是查询结果不是完整、一般用途的一致视图。

    When another claimant encounters a locked candidate, it skips the row instead of waiting. A queue consumer can continue looking for other work; if no other job is eligible, this call may return no row. The tradeoff is that the result is not a complete, general-purpose consistent view.

  4. Lease token and expiry / Lease token 与过期时间

    领取语句提交后，数据库行锁已结束，但 Worker 仍需要在一段时间内拥有处理权。后续续租/完成 SQL 通过 running 状态、当前 token 和未过期条件检查所有权。token 条件使接管后的旧 Worker 不能覆盖数据库中的新状态。

    After the claim statement commits, the database row lock is gone, but the worker still needs time-limited processing ownership. Later renewal/completion SQL checks the running status, current token, and unexpired lease. The token condition prevents an old worker from overwriting database state after a takeover.

关键边界 / Important boundary

这些机制不等于 exactly-once。假如 Worker 在 Lease 过期前已调用外部支付接口，但在写回完成状态前崩溃，新 Worker 可能重试该副作用。数据库拒绝旧 token 的 Finish，并不能撤销已经发生的外部操作。

These mechanisms do not provide exactly-once execution. If a worker calls an external payment API before its Lease expires but crashes before recording completion, a new worker may retry that side effect. Rejecting the old token's Finish in the database cannot undo an external operation that already happened.
